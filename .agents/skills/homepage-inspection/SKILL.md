# 홈페이지 점검 스킬

## 목적

공공기관 홈페이지를 읽기 전용으로 탐색하여 다음 사항을 점검한다.

- 페이지 접속 및 링크 오류
- 빈 페이지와 깨진 이미지
- 첨부파일 다운로드 오류
- 게시판 및 썸네일 콘텐츠의 최신 게시일
- 오래된 안내와 현행화 의심 콘텐츠
- 문구 오류와 표현 개선사항
- 이전 점검결과 대비 신규·지속·해결 항목

## 실행 전 확인

1. `references/inspection-targets.md`에서 점검 대상 URL과 범위를 확인한다.
2. `references/recency-rules.md`에서 게시 최신성 판단 기준을 확인한다.
3. `references/exclusion-rules.md`에서 제외 대상을 확인한다.
4. `previous` 폴더의 이전 결과가 있으면 읽는다.
5. `output`과 `screenshots` 폴더가 없으면 생성한다.

## 탐색 순서

1. 홈페이지 메인 화면에 접속한다.
2. 상단 메뉴와 하위 메뉴를 수집한다.
3. 사이트맵 또는 전체메뉴가 있으면 함께 확인한다.
4. 중복 URL을 제거한다.
5. 지정된 최대 페이지 수 또는 범위까지 순차적으로 접속한다.
6. 각 페이지는 전체 텍스트/HTML을 읽지 않고, 스크립트로 제목, URL, 본문 상태(정상/빈 페이지/오류), 주요 링크, 첨부파일 존재 여부만 추출하여 확인한다.
7. 게시일이 표시되는 목록형 콘텐츠가 있으면 첫 화면 최신 글의 게시일만 추출하여 확인한다. 목록 전체를 순회하지 않는다.
8. 오류 후보는 한 번 더 접속하거나 새로고침하여 재확인한다.
9. 명확한 오류에 대해서만 스크린샷을 저장한다.
10. 결과를 `output` 폴더에 작성한다.

## 필드 추출 방법 (토큰 절감)

- `webcheck` MCP 서버 (webcheck-mcp, `mcp-server/`)가 연결되어 있으면 아래 순서를 우선 사용한다.
  1. `check_links`로 URL 목록의 접속 가능 여부를 한 번에 확인한다. 브라우저로 하나씩 열지 않는다.
  2. `check_recency`로 `references/page-cache.md`에 `추출셀렉터`가 있는 게시판의 최신 게시일과 3개월 판정을 한 번에 받는다.
  3. 반환된 `수동확인필요` 항목만 브라우저로 직접 열어 확인하고, 새로 찾은 CSS 선택자를 `update_page_cache`로 `references/page-cache.md`에 기록한다.
  4. 그 외 오류 후보 재현, 문구 검토, 현행화 의심 판단 등 맥락 판단이 필요한 항목만 브라우저로 직접 연다.
- MCP 서버가 없거나 특정 페이지가 JS 렌더링이라 정적 요청으로 못 읽는 경우에만 브라우저 자동화로 대체한다. 이때도 페이지 전문(전체 텍스트/HTML)은 읽지 않고, 스크립트 실행으로 필요한 값만 뽑는다. 예:
  - 최신 게시일: `document.querySelector('.board_list tbody tr:first-child .date')?.innerText`
  - 페이지 상태 확인: `document.title`, `document.body.innerText.length === 0`
  - 깨진 이미지: `[...document.images].filter(img => !img.complete || img.naturalWidth === 0).map(img => img.src)`
- `page-cache.md`의 `추출셀렉터` 컬럼에는 순수 CSS 선택자만 저장한다 (예: `.board_list tbody tr:first-child .date`). `document.querySelector(...)`나 `.innerText` 같은 코드는 붙이지 않는다 — 이렇게 해야 브라우저의 `querySelector`와 MCP 서버의 `BeautifulSoup.select_one` 양쪽에서 동일한 값을 그대로 재사용할 수 있다.

## 게시 최신성 점검 절차

1. 게시판, 카드 목록, 썸네일 목록, 공지 목록, 보도자료, 행사, 자료실 등 목록형 영역을 찾는다.
2. 첫 페이지에서 게시일이 표시된 가장 최신 글을 확인한다.
3. 상단 고정글 여부를 확인한다.
4. 최신 글의 날짜를 `YYYY-MM-DD` 형식으로 정규화한다.
5. 기준일은 실행 당일 날짜를 사용한다.
6. 기준일에서 달력 기준 3개월 전 날짜를 계산한다.
7. 최신 게시일이 기준일의 3개월 전 날짜와 같거나 이전이면 `게시 최신성 지연`으로 분류한다.
8. 게시일을 찾지 못하면 `게시일 확인 불가`로 기록한다.
9. 비정기 게시 영역은 오류 확정보다 `담당자 확인 필요`를 병기한다.
10. 목록마다 최신 게시일, 기준일, 경과 기간, 판정 결과를 기록한다.

## 페이지별 점검 항목

- 페이지 정상 접속 여부
- 페이지 제목과 메뉴명 일치 여부
- 빈 페이지 여부
- 깨진 이미지 여부
- 내부 링크 오류
- 외부 링크 URL 이상 여부
- 첨부파일 다운로드 여부
- 오탈자와 부자연스러운 문구
- 종료된 행사 또는 사업의 현재형 안내
- 오래된 담당자·연락처·조직정보 의심
- 현재 연도와 맞지 않는 운영 안내
- 개인정보 또는 민감정보 노출 가능성
- 최신 글이 현재보다 3개월 이상 오래되었는지 여부

## 판정 원칙

- 확실한 사실과 추정을 구분한다.
- 근거가 부족하면 오류로 확정하지 않는다.
- 현행화 여부는 페이지의 목적과 기록 보존 필요성을 함께 검토한다.
- 과거 자료 및 기록물은 현행화 오류에서 제외한다.
- 동일 문제는 대표 URL 하나를 중심으로 정리하고 관련 URL을 병기한다.
- 게시 최신성은 게시물의 내용이 아니라 목록의 최신 게시일을 기준으로 판단한다.

## 결과 파일

점검 기준일을 `YYYY-MM-DD` 형식으로 파악하여 날짜 기준 폴더를 생성하고 작성한다. (예: 점검일이 2026-08-26 인 경우)

- `output/YYYY-MM-DD/inspection-summary.md` (예: `output/2026-08-26/inspection-summary.md`)
- `output/YYYY-MM-DD/inspection-details.csv` (예: `output/2026-08-26/inspection-details.csv`)
- `output/YYYY-MM-DD/recency-status.csv` (예: `output/2026-08-26/recency-status.csv`)
- `output/YYYY-MM-DD/unvisited-pages.md` (예: `output/2026-08-26/unvisited-pages.md`)

## inspection-summary.md 구성

1. 점검 개요
2. 종합 결과
3. 확정 오류
4. 게시 최신성 지연
5. 현행화 의심
6. 문구 개선사항
7. 담당자 확인 필요사항

9. 후속 조치 제안
