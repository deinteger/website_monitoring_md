# 평가 기준별 자기점검 (세션1: 필요성 20 · 창의성 30 · 활용성 20 · 완성도 15 · 확산가능성 15)

> 신청서·구동안내서를 쓸 때 강조할 점과 **약점**을 솔직하게 정리했다. 약점을 가리면 구동 심사에서 드러난다.

| 지표(배점) | 근거로 쓸 수 있는 것 | 약점·주의 |
| --- | --- | --- |
| **필요성(20)** | 정책정보 확인주간·홈페이지 품질관리는 매년 반복되는 범정부 점검이고, 체크리스트 22개 항목을 담당자가 수작업으로 확인한다 | 소요 시간·건수 같은 **정량 근거가 아직 없음**. 담당자 수작업 시간을 측정해 넣으면 설득력이 커진다 |
| **창의성(30)** | ① 사실은 스크립트·판단만 AI(역할 분리) ② AI 지적의 **원문 인용 검증으로 환각 차단** ③ 가이드라인을 **쪽·인용 근거 규칙 데이터**로 관리하고 개정판을 git으로 갱신 ④ 사람이 응답할 문항은 자동으로 채우지 않음 | 배점이 가장 큼. 점검 자동화 자체는 흔한 주제라 ①~④의 **설계 차별점**을 앞세워야 함. AI의 비중(현행화·오타·화면 검토)이 코드 비중보다 작아 보이지 않게 설명 필요 |
| **활용성(20)** | 실제 사이트에서 읽기 전용 확인으로 결함을 찾아 수정(스크립트 이동 껍데기 페이지, 한글 연락처 헤더 오류 등), 어제·그제 현행화 조회·담당자 연락처 질의 | 실제 기관 전체 점검 결과(기대효과 수치)는 제출 불가·미실시. **기대효과는 추정임을 명시** |
| **완성도(15)** | 표준 라이브러리 전용, 자동 테스트 99건, 데모 모드(접속·키 없이 구동), 운영 가이드·보안 통보 양식 | 정책정보·UI/UX 규칙팩이 **사람 검수 전**(`reviewed`)이면 그대로 밝힐 것. UI/UX 스타일·컴포넌트 규칙은 일부만 자동 |
| **확산가능성(15)** | 규칙·설정이 데이터라 다른 기관이 프로필만 바꿔 사용, 모델 비종속, 여러 에이전트 환경 지원, 배포 패키지 빌더 | 2종 이상 모델 구동 입증은 **API 키 필요**(미실시면 "구조상 가능, 입증은 …"이라고 정확히 표현) |

## 심사에서 제외될 수 있는 위험 (안내서 8. 유의사항)

1. 심사위원이 구동안내서대로 **구동할 수 없으면 제외** → 데모 모드를 첫 절차로 안내(구동안내서 2항)
2. 제출 서류 규격 미준수·항목 누락 → 파일명·분량(구동안내서 5쪽 이내)·양식 항목 확인
3. 마감 후 GitLab 변경 이력 → 마지막 커밋 전 `00_제출체크리스트` 4항 점검 완료
4. 표절·저작권 → 참고 자료·출처 명시(구동안내서 6항), 가이드라인 원문 이용 조건 확인
5. **민감자료 사용 금지(개발 단계)** → 제출 저장소에 실제 기관 점검 데이터가 없도록 `make_release.py` 산출물로 새 저장소 구성
